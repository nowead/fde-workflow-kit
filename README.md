# FDE Workflow Kit

시간 제한이 있는 실무형 AI 코딩 과제를 FDE(Forward Deployed Engineer)처럼 풀기 위한 **Codex 스킬 7개와 AGENTS.md 템플릿**입니다.

FDE처럼 푼다는 것은 이런 흐름입니다. 고객의 문제를 먼저 정의하고, 가장 작은 동작하는 결과를 빨리 만들고, 실행으로 증명하고, 결정과 한계를 기록으로 남깁니다.

이 저장소에는 **작업 방식만** 있습니다. 과제 정답 코드, MCP 서버, 에이전트, 프레임워크 설치 도구는 없습니다.

## 빠른 시작

작업 폴더(과제 README가 있는 곳)의 터미널에서 실행합니다.

```bash
git clone --depth 1 https://github.com/nowead/fde-workflow-kit /tmp/kit && bash /tmp/kit/install.sh .
codex
```

- 스킬은 `~/.agents/skills/`(Codex 사용자 범위)로 복사됩니다. 작업 폴더는 어지럽히지 않습니다.
- `.` 인자를 주면 작업 폴더에 `AGENTS.md`가 **없을 때만** 템플릿을 만듭니다.
- Codex에서 `/skills`나 `$`를 입력해 스킬 7개가 보이는지 확인합니다.
- 설치 스크립트는 파일 복사만 합니다. 네트워크 접속, 패키지 설치, Codex 설정 변경은 하지 않습니다.

| 상황 | 방법 |
| --- | --- |
| 스킬이 안 보임 | Codex 재시작 → 설치 없이 "`/tmp/kit/.agents/skills/kickoff/SKILL.md`를 읽고 따라줘" |
| 작업 폴더 안에 두고 싶음 | `bash /tmp/kit/install.sh . --repo` (`./.agents/skills`, 제출물에 포함됨) |
| 구버전 Codex | `--legacy` (`$CODEX_HOME/skills`에 복사). 제공된 환경에서는 지원 여부와 허용 범위를 확인하기 전에는 쓰지 않습니다 |
| 같은 이름의 스킬이 이미 있음 | 설치 스크립트가 건너뜁니다(`skip`). `--force`는 그 폴더를 지우고 교체하므로 시험이나 공용 환경에서는 쓰지 않습니다 |
| 설치가 막힘 (권한 거부 등) | 보안·샌드박스·승인 설정을 바꾸지 않습니다. 설치 없이 "`/tmp/kit/.agents/skills/<스킬>/SKILL.md`를 읽고 따라줘"로 대신합니다 |
| git clone 불가 | `curl -L https://github.com/nowead/fde-workflow-kit/archive/refs/heads/main.tar.gz \| tar xz -C /tmp && bash /tmp/fde-workflow-kit-main/install.sh .` |

## 흐름

사람이 칠 명령은 다섯 가지입니다: `$kickoff`, `$clarify`, "다음 슬라이스: …", `$checkpoint`, `$wrapup`. 그 사이에 구현 세션을 두 번쯤 새로 엽니다. 작업 상태는 모두 `docs/`와 git에 남으므로, 슬라이스가 커밋된 직후라면 세션을 새로 열어도 잃는 것이 없습니다.

### 창 구성

| 창 | 하는 일 | 여는 때 |
| --- | --- | --- |
| 터미널 1: 구현 세션 | `$kickoff`부터 `$wrapup`까지 모든 작업. 코드, 문서, 커밋은 이 세션만 바꿉니다 | 처음. 이후 [세션을 새로 시작할 때](#세션을-새로-시작할-때)의 시점마다 `/new` |
| 터미널 2: 설명 세션 | `codex` → `$explain`으로 시작해 모르는 용어, 개념, 코드를 묻습니다. 읽기만 합니다 | 첫 슬라이스의 코드가 생겼을 때. 문답이 길어지면 `/new` 뒤 다시 `$explain` |
| 담당자 메신저 | 업무 규칙, 우선순위, 데이터의 의미를 내 말로 묻습니다 | "담당자에게 확인할 것 준비됨"이 왔을 때 |
| 에디터 | `docs/stakeholder.md`에 대화를 붙여 넣고(사람만 고침), 슬라이스 보고의 읽을 곳을 엽니다 | 계속 |

설명 세션은 이렇게 답합니다.

- 코드에 있는 것: `file:function`과 이유
- 코드에 없는 개념: "우리 코드에는 없음"과 과제와의 연결
- 어느 쪽이든 끝에 확인 질문 하나

설명 세션은 구현 세션의 대화를 모릅니다. 방금 Codex가 한 일의 이유처럼 본 대화를 알아야 하는 질문은 구현 세션의 `/side`가 낫습니다.

### 단계별 진행 (3시간 과제 기준)

| 경과 | 단계 | 사람이 칠 것 | Codex가 일하는 동안 사람이 할 일 |
| --- | --- | --- | --- |
| 0:00 | 시작 | `$kickoff 남은 시간 2:55` | README와 제공 파일을 직접 읽고, 문제와 성공 기준을 내 말로 적어 둡니다. Codex가 정한 문제와 골든 패스를 판단하는 기준이 됩니다 |
| 0:10 무렵 | 담당자와 대화 | (Codex는 셋업을 끝내고 슬라이스 1을 시작) | 킥오프 보고 끝의 `확인:` 줄에 내 메모와 비교해 답합니다(예: "확인. 관리자 승인이 핵심이라" 또는 고칠 점). Codex는 답을 기다리지 않고 슬라이스 1을 이어 갑니다. 승인 대기가 없는지 본 뒤 메신저로 갑니다. requirements.md의 확인할 것을 위에서부터 내 말로 묻고, 대화를 `docs/stakeholder.md`에 붙여 넣습니다 |
| 0:30 무렵 | 대화 반영 | `$clarify` | 바뀐 요구사항과 출처 행, 충돌을 확인하고 "진행"이라고 답합니다. 충돌이 있으면 고른 쪽과 이유를 한 줄로 씁니다 |
| 0:40 무렵 | 세션 새로 1 | `/new` → `$kickoff 복구` | "진행" 뒤 첫 슬라이스 보고 끝에 `새 세션 시점` 줄이 오면 엽니다. 복구는 3줄로 보고하고 바로 다음 슬라이스를 이어 갑니다 |
| 구현 | 슬라이스 루프 | "다음 슬라이스: … 범위: … 유지: … 확인: …" | 슬라이스 보고의 **읽을 곳**(파일:함수와 이유)을 열어 읽고, 미리보기로 확인합니다. 모르는 것은 설명 세션에 묻습니다. 골든 패스가 동작하면 담당자에게 확인받고, 대화를 붙여 넣은 뒤 `$clarify`를 부릅니다 |
| 40분마다 | 체크포인트 | `$checkpoint 남은 시간 …` | 진행/중단을 물으면 결정과 이유를 한 줄로 답합니다 |
| D-40 (W), Must가 남았을 때 | 마무리 판단 | `$checkpoint 남은 시간 0:40` | 예상 시간과 되돌릴 커밋을 보고 진행/중단을 정합니다 |
| Must가 모두 PASS면 바로, 늦어도 D-25 (L) | 세션 새로 2 + 마무리 | `/new` → `$wrapup` | 먼저 오는 브리핑을 읽으며 사실과 다른 문장을 찾고, 질문(최대 3개)에 답합니다. 체크리스트가 나오면 "연습"이라고 해서 예상 질문에 직접 답해 봅니다 |
| D-10까지 | 제출 | | 체크리스트대로 제출합니다. 연습은 제출하기 전에 합니다 |

사람이 고른 것(충돌, 진행/중단, 범위 축소)과 미리보기에서 본 것은 사람이 한 말 그대로 `사람: "…"`로 기록됩니다. AI에게 판단을 넘긴 것이 아니라 사람이 검토하고 정했다는 흔적입니다.

### 세션을 새로 시작할 때

요청마다 그때까지의 대화 전체가 다시 입력으로 들어갑니다. 킥오프 세션에는 README, 제공 파일, 담당자 대화를 읽은 내용이 쌓여 있지만, 그 결과는 이미 requirements.md와 progress.md에 정리되어 있습니다. `/new` 뒤 `$kickoff 복구`는 다음만 읽고 3줄(어디까지 왔는지, 다음 할 일, 남은 시간)로 보고합니다.

- progress.md의 현재 상태
- requirements.md의 요구사항 표와 충돌
- `git log`와 `git status`

보고한 뒤에는 "다음 슬라이스"를 기다리지 않고 그 일을 바로 시작합니다. 다만 현재 상태가 사람의 답을 기다리는 중이면(예: `$clarify` 뒤 "진행" 전) 그 답을 묻고, 커밋되지 않은 변경(`docs/stakeholder.md` 제외)이 있으면 목록을 보여 주고 남길지 묻습니다.

| 시점 | 새 세션에서 칠 것 | 이유 |
| --- | --- | --- |
| "진행" 뒤 첫 슬라이스 보고 끝에 `새 세션 시점` 줄이 왔을 때 (권장) | `$kickoff 복구` | 남은 시간의 대부분인 구현 루프가 가벼워집니다 |
| `$wrapup` 직전 (권장) | 바로 `$wrapup` | 최종 점검과 브리핑이 쌓인 구현 대화가 아니라 docs, git, 코드를 보고 판단합니다 |
| `/status`의 컨텍스트 사용량이 절반을 넘었을 때 | `$kickoff 복구` | 이후 요청마다 그만큼이 다시 들어갑니다 |
| 같은 실수가 되풀이되거나 대화가 꼬였을 때 | `$kickoff 복구`와 바로잡을 점 한 줄 | 틀린 시도가 대화에 남아 다시 끌려가는 것을 끊습니다 |
| AGENTS.md를 고쳤을 때 | `$kickoff 복구` | AGENTS.md는 세션을 시작할 때만 읽힙니다 |
| 탭을 닫았거나 연결이 끊겼을 때 | `$kickoff 복구` | 상태는 `docs/`와 git에 있습니다 |

`/new` 전에 세 가지를 확인합니다. 하나라도 아니면 먼저 그것을 끝냅니다.

- **Codex가 멈춰 있다.** 실행 중이거나 승인을 기다리는 중이 아닙니다.
- **마지막 슬라이스가 커밋됐다.** 슬라이스 보고에 커밋이 있고, 작업 중인 변경이 없습니다. 슬라이스 도중에 열면 새 세션은 바뀐 파일은 보지만 그 의도는 모릅니다.
- **채팅으로만 한 말이 기록됐다.** 충돌 선택, 진행/중단, 범위 축소가 `사람: "…"`로 남았습니다. `$clarify`나 `$checkpoint`가 답을 기다리는 중이면 먼저 답합니다.

새 세션에서도 모델과 추론 강도는 그대로 둡니다(`/status`로 확인). `/compact`도 대화를 줄이지만 요약에 무엇이 남을지는 사람이 정하지 않습니다. 상태가 문서에 있으니 `/new`와 복구가 더 예측 가능합니다.

### 기다리는 시간을 쓰는 법

- Codex가 실행 중일 때 같은 요청을 또 보내지 않습니다. 방향이 틀렸으면 `Esc`로 멈추고 한 번에 정정합니다.
- 구현 세션에는 작업 지시만 보냅니다. 질문은 설명 세션으로 보냅니다.
- 슬라이스 지시에는 범위, 지킬 것, 확인 방법을 넣습니다. 작업 기록을 보는 사람은 프롬프트에서 사람이 목표와 제약을 정했는지 봅니다. 예: `다음 슬라이스: R4 예약 취소. 범위: 본인 예약만. 유지: R1-R3 동작과 API는 그대로. 확인: test_R4 추가 후 check, 미리보기에서 취소 버튼`
- 슬라이스 보고나 읽을 곳에서 요구하지 않은 장치(잠금, 캐시, 재시도, 추가 계층)가 보이면 빼라고 지시합니다. 그 지시가 사람이 설계를 통제한 기록이 됩니다.
- 같은 종류의 안전한 명령이 승인을 반복해서 물으면 이번 세션 동안 허용합니다. 모르는 명령은 읽고 정합니다.
- "요청 완료"와 "과제 완료"는 다릅니다. 슬라이스 보고의 `check` 결과를 봅니다.

### 스킬

| 스킬 | 언제 | 하는 일 |
| --- | --- | --- |
| `$kickoff` | 시작할 때, 새 세션에서 이어 갈 때 | 마감, 목표 종료, 마무리 판단·한계 시각 설정. 문제와 성공 기준, 골든 패스 정의. 과제 크기에 맞춘 작업 기록(담당자에게 확인할 것 포함), 과제가 요구하는 문서의 초안, `check` 명령을 만든 뒤 바로 슬라이스 1 시작. 보고 끝의 확인 줄로 사람이 문제·골든 패스·스택을 확인 |
| `$clarify` | 담당자와의 대화를 `docs/stakeholder.md`에 붙여 넣었을 때, 요구사항이 모호할 때 | 새로 붙인 대화만 읽고 requirements.md 갱신(요구사항과 출처 행, 수용 기준, 충돌, 자동 가정, 새로 확인할 것). 사람이 확인할 때까지 멈춤. 사람이 충돌을 고르면 그 말과 이유를 그대로 ADR에. 킥오프 세션에서 "진행"을 받으면 다음 슬라이스 보고 끝에 새 세션을 열 시점을 알림 |
| `$checkpoint` | 40분마다, 일정이 밀릴 때, 마무리 판단 시각 | 남은 시간 대비 남은 일 판단. Must가 다 끝났으면 **조기 마무리**, 마무리 판단 시각에 Must가 남았으면 **진행/중단 판단**. 범위를 바꾸는 결정은 사람의 답과 이유를 받아 기록 |
| `$audit` | `check`보다 깊은 확인이 필요할 때 | 요구사항별 실행 증거, PASS/FAIL/UNVERIFIED, 제출 준비 판정. 사람이 미리보기에서 본 결과도 그대로 기록 |
| `$wrapup` | Must가 모두 PASS일 때, 마무리 판단 시각에 남은 Must를 접기로 했을 때, 늦어도 마무리 한계(D-25) | 동결 → 최종 점검 → 브리핑(사람이 읽는 동안 Codex는 문서 마무리) → 제출 체크리스트를 한 번에 |
| `$debrief` | 리뷰어나 고객에게 작업을 직접 설명하고 방어해야 할 때 | 사실 확인을 거친 브리핑(호출 흐름, 상태와 검증 위치, 핵심 숫자와 공식, 결정의 장단점, 도구 구성, 한계와 막지 않은 근거), 문서와 구현의 차이, 리뷰어가 물을 만한 질문의 답 뼈대. "연습"이라고 하면 질문을 하나씩 묻고(하나는 전제가 틀린 질문) 사람의 답을 코드 기준으로 바로잡음 |
| `$explain` | 모르는 용어·개념·코드가 나왔을 때 (두 번째 터미널에서) | 읽기만 하고 답함: 뜻, 우리 코드의 위치와 이유(코드에 없으면 "우리 코드에는 없음"과 과제와의 연결), 확인 질문 한 줄. 문제를 찾으면 고치지 않고 "구현 세션에 가져갈 것"으로 알림 |

사용 요령:

- `$checkpoint`
  - 남은 시간은 화면 타이머를 그대로 읽어 줍니다. 마감이 바뀌면 W와 L도 같은 간격으로 옮겨집니다.
  - 40분마다 외에도, 슬라이스가 예상보다 50% 넘게 길어지거나 한 문제에서 10분째 진전이 없을 때 부릅니다.
  - "확인:" 줄에는 "진행" 또는 "중단"과 이유 한 줄을 답합니다. 진행을 골랐으면 중단 기준 줄의 커밋을 기억해 둡니다.
- `$audit`
  - 구현 중에는 `check`로 충분합니다. `$audit quick`은 위험한 곳을 건드린 슬라이스 뒤나, "됐다"는 말이 미심쩍을 때 씁니다.
  - 화면 확인은 사람이 미리보기에서 본 것을 내 말로 알려 줘야 PASS가 됩니다.
  - `$wrapup`이 final 모드를 직접 돌리니, 그 직전에 따로 부르지 않습니다.
- `$wrapup`
  - `/new` 뒤에 부릅니다.
  - 중간에 오는 브리핑이 제출 전 마지막 공부 시간입니다. 맨 위의 문서와 구현의 차이부터 읽습니다.
  - 나만 아는 사실을 묻는 질문(최대 3개)에는 짧게 답합니다. 답하지 않으면 "기록 없음"으로 남습니다.
  - READY WITH RISKS는 정상적인 결과입니다. 남은 위험은 한계로 설명합니다.
- `$debrief`
  - "연습"은 제출 전에 합니다. 문서를 보지 않고 직접 쳐서 답합니다.
  - 첫 문제나 둘째 문제는 전제가 틀린 질문입니다. 답할 때 차이부터 밝힙니다.
  - 브리핑에서 "사후 설명"이 붙은 결정은 기록된 이유가 없는 가장 약한 곳이니 먼저 준비합니다.
  - 핵심 숫자는 값, 공식, 계산하는 함수를 함께 말할 수 있게 준비합니다.
  - 도구를 이렇게 구성한 이유(스킬, 세션 분리)와, 일부러 넣지 않은 것의 이유를 내 말로 말할 수 있게 준비합니다.
  - 설명 세션에서는 부르지 않습니다.
- 공통: 내가 답한 말은 그대로 기록됩니다. 나중에 설명할 문장으로 답합니다. 예: "진행. 주간 노선이 우선순위 1이라서".

### 마무리 시각

**최소 시간은 없습니다.** Must가 모두 PASS이거나 사람이 한계로 인정하면, 남은 시간과 상관없이 `$wrapup`으로 마무리합니다. 남는 시간에 기능을 덧붙이면 토큰, 회귀 위험, 설명해야 할 코드가 모두 늘어나기 때문입니다.

Must가 남아 있을 때는 무조건 동결하지 않습니다. 마무리 시각을 둘로 나눕니다.

- **마무리 판단 시각 W**: 전체 시간의 약 20%가 남았을 때(3시간 과제면 D-40). 여기서 `$checkpoint`가 남은 Must마다 진행/중단을 판단합니다. 세 조건이 모두 맞을 때만 진행합니다.
  - 구현과 검증까지의 예상 시간 ×1.5가 L까지 남은 시간 안에 들어간다.
  - 지금 상태가 커밋되어 있고 `check`가 통과해서, 실패하면 한 번에 되돌릴 수 있다.
  - 이미 PASS한 Must와 골든 패스의 코드를 건드리지 않는다. 건드린다면 `check`가 그 Must를 모두 검사한다.
- **마무리 한계 L**: D-25(압축 마무리 15분과 제출 여유 10분). 진행한 Must가 L까지 PASS가 아니면 직전 커밋으로 되돌리고 한계로 기록한 뒤 `$wrapup`을 시작합니다. 최종 점검과 제출 시간은 어떤 경우에도 기능에 쓰지 않습니다.

`$wrapup`의 최종 점검이 READY(또는 READY WITH RISKS)이고, 문서가 최신이고, 사람이 작업을 설명할 수 있으면 끝입니다.

## 담당자와의 대화

세부 요구사항은 사람이 담당자에게 직접 묻고 알아냅니다. Codex는 담당자에게 보낼 메시지를 쓰지 않습니다.

1. `$kickoff`가 README에서 목적과 요구사항을 정리하고, requirements.md에 **확인할 것**을 만듭니다. 각 항목은 질문, 왜 중요한지, 답이 없을 때 쓸 기본값입니다. README에 없는 배경(누가 쓰는지, 지금은 어떻게 하는지)을 묻는 질문이 먼저 오고, 담당자가 여럿이면 물을 사람이 붙습니다.
2. 사람은 README와 requirements.md를 옆에 띄워 두고 자기 말로 묻습니다. 모르는 업무 용어와 배경도 담당자에게 먼저 묻습니다. 대화는 `docs/stakeholder.md`에 붙여 넣습니다. 직접 요약한 부분은 (요약)이라고 표시하고, 담당자가 여럿이면 대화마다 `## <이름·역할>` 제목을 붙입니다.
3. `$clarify`는 새로 붙인 부분만 읽습니다. 요구사항은 출처(담당자, 몇 행, 원문 한 줄)와 함께 적고, README나 다른 답과 어긋나면 충돌로 표시하고 그 일을 맡은 담당자의 최신 답을 제안합니다(주최 측 규칙이나 제출물과 부딪히면 예외). 답에서 새로 생긴 빈틈은 확인할 것에 더합니다. 그리고 멈춥니다.
4. 사람이 requirements.md를 확인하고, 충돌이 있으면 고른 뒤 "진행"이라고 하면 구현을 이어 갑니다. 동작을 보여 주고 확인받는 대화도 같은 방식으로 반복합니다.

## 작업 기록 (작업 공간의 `docs/`)

중요한 것은 문서 형식이 아니라 남는 내용입니다. 요구사항과 그 출처, 검증 결과, 결정과 근거를 남깁니다.

| 문서 | 쓰는 쪽 | 내용 |
| --- | --- | --- |
| `docs/requirements.md` | Codex (사람은 읽기) | 목적(문제, 성공 기준, 골든 패스, 산출물), 요구사항(상태, 출처, 수용 기준, 검증 결과), 충돌, 확인할 것 |
| `docs/stakeholder.md` | 사람만 | 담당자와 나눈 대화 원문 또는 요약 |
| `docs/adr/NNNN-*.md` | Codex | 중요한 결정 하나당 한 파일: 맥락 → 선택지 → 결정 → 결과 → 출처 |
| `docs/progress.md` | Codex | 현재 상태(새 세션은 여기부터 읽음), 슬라이스 표, 시간순 로그(대화를 몇 행까지 반영했는지, AI 협업, 검증). 마지막에 최종 결과 |

- stakeholder.md를 사람만 고치는 이유: 에디터에 열어 둔 파일을 AI가 고치면 자동 저장이 멈추거나 붙여 넣은 내용이 덮일 수 있습니다.
- `$kickoff`가 과제 크기를 보고 형식을 고릅니다. Must가 3개 이하이고 과제가 결정 기록을 따로 요구하지 않으면 **압축** 형식입니다. `docs/adr/` 대신 requirements.md의 결정 섹션에 결정을 남기고, 결정이 3개를 넘으면 `docs/adr/`로 옮깁니다. 그 밖에는 **전체** 형식으로 네 문서를 모두 씁니다.

과제가 다른 문서를 요구하면(예: `PLAN.md`), `$kickoff`가 이 문서들을 링크하는 짧은 초안으로 만들고, 계획이 바뀌면 고치고, 마무리에서 완성합니다. 내용을 중복해서 관리하지 않습니다. 계획이 구현보다 먼저 있었다는 것이 커밋 이력에 남습니다.

## AGENTS.md 템플릿

`templates/AGENTS.md`는 매 요청에 들어가는 상시 규칙이라 짧은 영어로 썼습니다(o200k 토크나이저로 약 1,410토큰). 스킬은 이름과 설명만 매 요청에 들어가고(7개 합계 약 520토큰), 본문은 부를 때 읽힙니다. 작성자 환경(Codex 0.165)에서 잰 매 요청 고정 입력 약 14,000토큰에 견주면 키트 몫은 약 14%입니다.

- 금지 사항(비밀값과 제공 데이터의 개인정보 포함). 과제가 제공된 뼈대 코드 위에 만들라고 하면 그 코드는 그 자리에서 고칩니다
- 슬라이스 루프: 구현과 수용 기준 테스트(이름에 요구사항 ID) → `check` → 문서 → 커밋(메시지에 요구사항 ID) → 슬라이스 보고. 업무 규칙 하나는 한 곳에
- 슬라이스 보고 형식: 남은 시간, 읽을 곳, 미리보기, 가정·결정, 다음
- 서브에이전트: 도구가 이미 있을 때, 읽기 전용 작업(큰 코드베이스 파악, 최종 점검의 독립 검토)에만
- 문서 규칙, 마무리 규칙, 스킬 지도

보고와 문서는 과제 언어(기본 한국어)로 쓰도록 지시합니다. Codex는 세션을 시작할 때 AGENTS.md를 읽으니, 고친 뒤에는 `/new`로 새 대화를 시작해야 반영됩니다.

## 토큰과 대기 시간

요청마다 그때까지의 대화 전체가 다시 입력으로 들어갑니다. 그래서 토큰은 답변 길이보다 대화 길이가 좌우합니다. 언제 새 대화를 여는지는 [세션을 새로 시작할 때](#세션을-새로-시작할-때)에 있습니다.

- 모델은 시작할 때 정하고 세션 중에는 바꾸지 않습니다(캐시는 모델마다 따로입니다). 추론 강도는 막힌 문제에서만 올립니다. 허용된 모델과 설정 규칙은 환경 안내를 따릅니다.
- Codex가 승인을 기다리는 동안에는 작업이 멈춥니다. 담당자 대화 창으로 가기 전에 승인 대기가 없는지 봅니다. 설치처럼 승인이 필요한 일은 `$kickoff`가 사람이 터미널에 있을 때 먼저 합니다.
- 서브에이전트를 켜려고 설정을 바꾸지 않습니다. 도구가 이미 있을 때만 AGENTS.md의 조건대로 씁니다.
- 모르는 것을 구현 세션에 물으면 그 문답이 이후 모든 요청에 다시 실립니다.
  - 두 번째 터미널의 `$explain` 세션에 물으면 그 세션에만 쌓이고, 구현을 기다리는 동안 바로 물을 수 있습니다.
  - Codex의 `/side`도 본 대화를 건드리지 않습니다. 하지만 본 대화 전체를 물려받아 질문마다 그만큼 입력이 들고, 임시 대화라 세션 기록에 남지 않습니다.
  - 설명 세션은 git의 index 잠금을 잡지 않는 명령만 써서, 구현 세션의 커밋과 부딪히지 않습니다.

## 제한된 환경에서 쓸 때

환경의 규칙과 과제별 규칙이 이 문서보다 우선합니다.

- 제공된 Codex만 씁니다. 업데이트를 권해도 업데이트하지 않습니다.
- 설치가 막혀도 보안·샌드박스 설정은 바꾸지 않습니다. `--force`와 `--legacy`는 쓰지 않고, SKILL.md를 직접 읽게 하는 방식으로 대신합니다.
- 공개 저장소는 clone할 수 있지만 push, 업로드, 문제·파일·결과물의 외부 전송은 하지 않습니다.
- Computer Use 같은 화면·브라우저 자동 조작, 외부 AI 연결, 환경 통제 우회는 하지 않습니다. 화면 확인은 사람이 미리보기에서 직접 합니다.
- 외부 자료로 결과물을 통째로 대체하지 않습니다. 이 저장소에는 정답 코드가 없습니다.

## 만든 방식

원칙과 실패 유형은 작성자가 정의했고, 스킬 초안은 AI 에이전트로 작성했습니다.

같은 모의 과제를 스킬 없이(기준선), 그리고 스킬을 적용해 실행하고 결과를 비교했습니다. 기준선에서 관찰된 실패는 이렇습니다.

- 검증 없이 한 번에 몰아서 구현
- 커밋 누락
- `127.0.0.1` 바인딩으로 미리보기 불가
- 과제 README와 담당자 답변의 충돌을 조용히 넘기기
- 마감 직전 기능 추가

스킬은 이 실패들을 막도록 고쳤고, 재테스트로 개선을 확인했습니다.

담당자 대화 흐름은 이전 버전과 같은 대화로 비교했습니다. 이전 버전은 대화를 정리한 뒤 사람의 확인 없이 바로 구현했고, 대화 원문을 요구사항 문서에 복사했습니다. 지금 버전은 세 번 모두 사람의 확인 전에 멈췄고, 출처는 행 번호와 핵심 구절로 답니다.

슬라이스 보고, 사람의 판단 기록, 브리핑 순서, 연습 모드를 더한 개정은 같은 모의 과제(회의실 예약 규칙, Python)의 네 장면을 이전 버전과 지금 버전으로 한 번씩 실행해 비교했습니다.

| 장면 | 이전 버전 | 지금 버전 |
| --- | --- | --- |
| 새 과제 시작 | 제공된 뼈대 코드를 고치면서 AGENTS.md 규칙의 예외라며 결정을 따로 남기고 사람에게 확인을 요청. PLAN.md 초안 없음, 테스트 이름에 요구사항 ID 없음, 보고에 스택과 읽을 곳 없음 | 뼈대를 그 자리에서 수정, 킥오프 커밋에 PLAN.md 초안, `test_R1_…` 형식 테스트, 질문 목록을 셋업보다 먼저 알림, 보고에 스택과 읽을 곳 |
| 새 세션에서 복구 | 세부 규칙(본인만, 30분 전까지)을 지켜 구현, 테스트 이름에 ID 없음 | 같은 구현, `test_R3_…` 테스트, 슬라이스 보고에 읽을 곳 |
| 마무리 판단 시각의 진행/중단 | 이유를 묻지 않음. 기록에는 "No-go 수용"만 남음 | 결정과 이유를 묻고, 로그와 결정 기록에 사람의 말을 그대로 남김 |
| 마무리 | 브리핑이 맨 끝에 옴. 브리핑이 찾은 한계(유령 예약)가 문서에 들어가지 못함 | 브리핑이 문서 마무리 전에 오고, 찾은 한계가 최종 문서에 들어감. "연습"에서 전제가 틀린 질문을 던지고 답을 코드 기준으로 바로잡음 |

복구 모드가 요구사항을 놓치는 실패는 이전 버전에서도 재현되지 않았습니다(요구사항 표를 읽게 한 것은 보험입니다). 토큰 사용량은 장면마다 두 버전이 비슷했습니다. 담당자 대화 정리의 새 보고 줄, 웹 미리보기 기록, 서브에이전트 검토는 이번 비교에 넣지 않았습니다.

평가 기준(기술·의도·인지)에 맞춘 개정은 시험 조건 프로필(같은 모델, 추론 강도, 샌드박스)의 Codex로 세 장면을 이전 버전과 지금 버전으로 한 번씩 실행해 비교했습니다. 담당자가 둘인 좌석 신청 과제와 결과 숫자가 있는 정산 과제(Python)를 썼습니다.

| 장면 | 이전 버전 | 지금 버전 |
| --- | --- | --- |

심어 둔 개인정보 노출(리포트의 탑승자 연락처, 로그의 전화번호)은 두 버전 모두 마무리 점검에서 찾아 지웠습니다. AGENTS.md의 개인정보 규칙은 구현 중 예방을 위한 것이며, 이번 비교로는 그 효과를 확인하지 못했습니다. 브리핑의 "일부러 넣지 않은 것"과 "감수한 것"은 지금 버전에서도 따로 나오지 않았습니다. 대화 정리 장면에서는 지금 버전이 입력 토큰을 더 썼고(157k → 242k), 나머지 장면은 시간과 토큰이 비슷했습니다. 비대화형 실행이라 승인을 줄 수 없어서, 샌드박스가 읽기 전용으로 둔 `.git`에 두 버전 모두 커밋하지 못했습니다.

모의 실행도 AI 에이전트로 했으므로, 실제 환경에서는 짧은 리허설을 권합니다.
